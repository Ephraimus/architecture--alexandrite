# Архитектурное решение по кешированию

## 1. Мотивация

Операторы в MES сталкиваются с низкой скоростью загрузки списка заказов: при переходе на страницу «Заказы» системе требуется время, чтобы выполнить запрос к базе данных, отфильтровать заказы, отсортировать их, возможно, агрегировать данные и только после этого отобразить результат. При росте числа заказов этот процесс ещё сильнее замедляется.

Кроме того, клиенты (особенно новые партнёры по API) тоже жалуются на долгую обработку заказа. Причина не только в вычислительных процессах расчёта стоимости, но и в задержках при частых обращениях к базе данных для чтения и обновления статусов. 

**Цель кеширования**: разгрузить базу данных MES и улучшить время ответа на операции чтения, особенно для часто запрашиваемых данных (список заказов, короткие сводки, статусы).

Мы планируем:
1. **Закешировать список заказов** (и их основные поля) для операторов MES, чтобы не обращаться к базе данных всякий раз при открытии страницы.  

Таким образом, кеширование должно:
- Ускорить операции чтения (просмотр списка заказов) за счёт выдачи данных из памяти (или быстро доступного хранилища).  
- Сократить время отклика MES-интерфейса и снизить нагрузку на базу.  
- Обеспечить при этом разумный баланс между актуальностью данных и скоростью чтения.

## 2. Предлагаемое решение

### 2.1 Тип кеширования

- **Серверное кеширование**:  
  - Выбираем его, т.к. главная проблема — высокая нагрузка на бэкенд и базу данных, а не избыточный трафик между клиентом (браузером) и сервером.  
  - Цель — ускорить именно бэкенд-операции с данными (частые SELECT-запросы) и разгрузить инфраструктуру MES.

- **Паттерн «Cache-Aside» (a.k.a Lazy Loading)**:  
  - При чтении: если данные есть в кеше — возвращаем сразу. Если нет — берём из БД и складываем в кеш.  
  - При записи/обновлении: сначала пишем в БД, а затем **инвалидируем** (или обновляем) кеш, чтобы при следующем чтении данные перезагрузились заново.  
  - **Почему не «Write-Through»**? Он хорош там, где нужно всегда синхронно поддерживать кеш в актуальном состоянии, но тогда каждое обновление нагружает и базу и кеш. При интенсивном потоке обновлений списка заказов может быть лишняя нагрузка.  
  - **Почему не «Refresh-Ahead»**? Он подразумевает предзагрузку данных в кеш до того, как они понадобятся, что сложно точно предсказать для заказа, так как меняется статус «рывками» (операторы берут в работу, клиенты формируют новые заказы в разное время).

## 2.3 Стратегия инвалидации

**Программная инвалидация (по ключу)**  
Каждый раз при изменении статуса заказа мы удаляем ключ из кэша, чтобы при последующих запросах получить обновлённые данные из базы. Причём ключи **формируются с учётом фильтров** (например, `ordersList:filter=status=NEW&page=1`), чтобы разные сегменты данных не конфликтовали друг с другом.

**Временная (TTL)**  
Можно поставить небольшой срок жизни (например, 5–10 минут) для дополнительной подстраховки, если вдруг в коде будет пропущена какая-то операция, меняющая список заказов. Однако основным механизмом синхронизации данных остаётся программная инвалидация.

| **Стратегия**                   | **Плюсы**                                                         | **Минусы**                                                                 |
|---------------------------------|-------------------------------------------------------------------|------------------------------------------------------------------------------|
| Программная (по ключу)          | Самая точная актуальность; сразу после обновления данные не устаревают | Требует явной логики: нужно следить, где и когда очищать кэш                 |
| TTL-только                       | Не требует кодовых доработок для инвалидации                      | Может показывать устаревшие данные до истечения TTL                          |
| Гибрид: программная + TTL       | И актуально, и «запасной парашют» на случай пропуска              | Сложнее в настройке, возможно лишняя нагрузка                                |

## 3. Заключение

Я предлагаю **Cache-Aside** (серверное кеширование) для списка заказов:

1. **Основная выгода** — ускорение чтения при открытии страницы MES, где операторы работают с большим объёмом заказов.  
2. **Ключи в кеше** формируются с учётом переданных фильтров (например, `ordersList:filter='status=...&page=...'`), чтобы разные варианты выборки не мешали друг другу.  
3. **Инвалидация**: при каждом изменении статусов заказов мы удаляем соответствующие записи в кеше, чтобы не показывать устаревшие данные.  
4. **TTL**: дополнительно можно настроить в несколько минут — на случай, если по каким-то причинам инвалидация была пропущена.

Ожидается, что такое решение существенно разгрузит базу и ускорит время ответа MES на чтение заказов. В будущем, если появятся другие сценарии с частыми повторными чтениями (например, результаты сложных расчётов), мы сможем расширить идею кеша и для них.
