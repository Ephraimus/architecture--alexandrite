## Мотивация

Сейчас бизнес опирается только на данные из Яндекс Метрики, которые показывают статистику по сайту онлайн-магазина. Однако с ростом заказов через публичный API и увеличением роли MES и CRM эти данные уже не отражают реальную картину. Без мониторинга системы мы не знаем:

- Где «узкие места» и как оперативно отреагировать на снижение производительности или сбои.  
- Как увеличивается нагрузка со стороны B2C (онлайн-магазин) и партнёров (API), и достаточно ли текущих мощностей.  
- Сколько реального времени уходит на жизненный цикл заказа (переходы по статусам от создания до отгрузки).

Добавление мониторинга позволит:
1. **Ускорять реакцию на инциденты** и сокращать простой.  
2. **Прогнозировать нагрузку** и своевременно увеличивать ресурсы.  
3. **Поддерживать клиентов** (включая партнёров по API) на высоком уровне сервиса.  
4. **Получать отчётливую аналитику** для принятия бизнес-решений о приоритетах развития.

Таким образом, инвестиции в мониторинг — это вклад в устойчивость и дальнейший рост бизнеса, особенно учитывая постоянное повышение числа заказов и интеграции с внешними компаниями.

## Выбор подхода к мониторингу

Для распределённой системы, где есть несколько сервисов (Shop API, CRM API, MES, RabbitMQ, базы данных), удобно сочетать разные методики:

1. **«Четыре золотых сигнала» (Latency, Traffic, Errors, Saturation)** для HTTP-сервисов (Shop, CRM, MES).  
2. **RED (Rate, Errors, Duration)** подход для RabbitMQ, чтобы смотреть на скорость обработки сообщений, число ошибок и время обработки (при необходимости).  
3. **USE (Utilization, Saturation, Errors)** для анализа системных ресурсов (CPU, память, дисковая I/O) на уровне инстансов и баз данных.

Такое комбинированное решение даёт максимально полную картину:
- **HTTP-сервисы**: следим за временем ответа, кодами ответов, количеством запросов и «нагруженностью» системы.  
- **Очередь (RabbitMQ)**: смотрим скорость прохождения сообщений, ошибки (dead-letter) и накопление «пробки» (количество сообщений в ожидании).  
- **Инфраструктура**: контролируем загрузку CPU, памяти, соединений к БД и другие системные метрики.

## Метрики и их назначение

Ниже перечислены основные метрики, которые мы считаем критичными для наблюдения. Каждая метрика может иметь **лейблы (labels)** — это дополнительные поля для фильтрации и анализа (например, по окружению `env=dev|release|prod` или по типу запроса `method=GET|POST`).

### 1. Метрики HTTP-сервисов (Shop API, CRM API, MES API)

- **Number of requests (RPS)**  
  Зачем: Показывает нагрузку на сервис.  
  Лейблы: `service` (Shop/CRM/MES), `method` (GET/POST/...), `endpoint` (URL pattern).
  
- **Response time (latency)**  
  Зачем: Определяет, не превышает ли время ответа установленный SLA.  
  Лейблы: `service`, `endpoint`, `statusCode` (200, 400, 500), чтобы видеть распределение по типам ответов.

- **Number of HTTP 200** и **Number of HTTP 500**  
  Зачем: Позволяют быстро отследить успешные вызовы и сбои.  
  Лейблы: `service`, `endpoint`.  

- **CPU % / Memory Utilisation** для Shop, CRM, MES  
  Зачем: Контроль использования системных ресурсов. Если сервис начинает «захлёбываться», это сразу заметно по росту CPU/Memory.  
  Лейблы: `service`, `instanceId`.

- **Kb transferred (received) / Kb provided (sent)**  
  Зачем: Оценить объём трафика (входящего/исходящего). Важно для понимания, не упирается ли приложение в пропускную способность сети.  
  Лейблы: `service`, `direction` (in/out).

### 2. Метрики RabbitMQ

- **Number of messages in flight**  
  Зачем: Показатель «пробки» в очереди, если сообщений слишком много, это признак замедления обработки.  
  Лейблы: `queueName`, `consumerGroup`.

- **Number of dead-letter-exchange letters**  
  Зачем: Видим, сколько сообщений «вывалилось» в DLX по ошибке. Высокое число — индикатор проблем при обработке.  
  Лейблы: `queueName`, `errorType` (если различаем тип ошибки).

### 3. Метрики баз данных

- **Memory Utilisation** (например, для shop DB, MES DB)  
  Зачем: При превышении критического уровня памяти база данных может замедлиться или упасть.  
  Лейблы: `dbName`.

- **Number of connections**  
  Зачем: Показывает, не исчерпаны ли подключения. При достижении лимитов сервисы могут «отваливаться» по timeout.  
  Лейблы: `dbName`.

- **Size of DB instance (Shop / MES)**  
  Зачем: Понимать, когда подходит время расширять хранилище.  
  Лейблы: `dbName`.

### 4. Дополнительные метрики

- **Size of S3 storage**  
  Зачем: Отслеживать рост загружаемых 3D-моделей и других файлов, чтобы вовремя планировать расширение.  
  Лейблы: `env` (тест/прод).

- **Number of simultanious sessions** (Shop, CRM, MES)  
  Зачем: Понимать пиковую активность пользователей; важно при планировании масштабирования.  
  Лейблы: `service`.

> **Примечание:** Метрики вроде _RPS per user_ можно включить, если мы хотим отслеживать поведение отдельных партнёров или крупных клиентов (для API). Тогда лейбл `userId` станет критическим, но может резко увеличить объём собираемых метрик.

## План действий (Draft ТЗ)

1. **Выбрать решение для мониторинга**  
   - Использовать Prometheus и Grafana.  
   - Настроить сбор метрик с сервисов (Shop, CRM, MES), RabbitMQ и баз данных.  

2. **Развернуть time-series хранилище**  
   - Создать инстанс Prometheus (либо использовать Managed Service, если доступно).  
   - Настроить сервис-дисковери или статические конфиги для парсинга `/metrics` endpoint-ов.

3. **Настроить агрегацию логов** (централизованное логирование)  
   - Использовать Elasticsearch/Logstash/Kibana (ELK) или любой другой стэк (Graylog, Splunk).  
   - Подключить все сервисы и окружения, установить поля для корреляции (requestID, traceID и т.д.).

4. **Конфигурировать дашборды и алерты**  
   - Создать Grafana-дашборды для API-сервисов (RPS, latency, HTTP 5xx и т.д.).  
   - Создать дашборд для RabbitMQ (сообщения в очереди, DLX) и для баз данных (memory, connections).  
   - Настроить алерты (например, Slack/Telegram/Email) при превышении критических порогов.

5. **Внедрить end-to-end метрики** (при необходимости)  
   - Если хотим видеть общий путь заказа: замерять время прохождения через статусы (INITIATED → FILE_UPLOADED → … → SHIPPED).  
   - Это может быть сделано на уровне CRM/MES как бизнес-метрика (например, `order_processing_time_seconds`).

6. **Обучить команду**  
   - Объяснить, как пользоваться дашбордами, где смотреть логи, как реагировать на инциденты.  
   - Договориться о базовых SLA/SLO/SLI и процедурах эскалации.

## Показатели насыщенности и реагирование

Для каждой ключевой метрики устанавливаются **пороговые значения**, при достижении которых система должна сигнализировать:

- **CPU Utilisation > 80%** в течение 5 минут:  
  - Оповещение в Slack/Email.  
  - DevOps анализирует, нужна ли оптимизация или добавление инстансов.

- **Memory Utilisation > 90%**:  
  - Тикет на проверку сервиса и перезапуск/расширение памяти.  
  - При повторных случаях — решение о горизонтальном/вертикальном масштабировании.

- **Response time (p95) > 2 секунд** на протяжении 10 минут:  
  - Алерт в канал с дежурными.  
  - Выяснить, не упирается ли сервис в базу данных, сеть или внутри есть блокирующая операция.

- **Number of dead-letter-exchange letters > X** (задаётся бизнес-порог, например, 1000 сообщений в час):  
  - Проверить логи, найти причину недоставки (битые сообщения, ошибочный routing key и т.д.).  
  - При подтверждении сбоя — срочный тикет на исправление кода или конфигурации.

- **Количество соединений к DB > 90%** от максимально допустимого**  
  - Алерт DevOps, временное ограничение на новые запросы или масштабирование БД-нод.

Если при превышении порогов команда не успевает устранить проблему своевременно, может срабатывать:
- **Автоматический запуск дополнительных инстансов** (autoscaling).  
- **Оповещение ответственных лиц** по SMS/телеграмме, если Slack-уведомление проигнорировано.

Такой подход позволяет своевременно предотвращать простои, сохранять стабильность системы и поддерживать высокое качество обслуживания клиентов.
